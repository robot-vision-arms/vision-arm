# 포트폴리오: 비전 기반 나사·너트 Pick & Place (ROS2 · Gazebo · UR5e)

> 휴대폰 카메라로 실제 나사·너트의 위치(mm)와 방향(도)을 구하고, TCP 로 로봇 컨트롤러에 보내고,
> Gazebo 속 UR5e 가 MoveIt2 로 그 부품을 집어 종류별 상자에 넣는 시스템.

## 1. 문제 정의

- 로봇은 **mm 단위 좌표**와 **각도**로 움직이지만, 카메라가 주는 것은 **픽셀(px)** 이다. 렌즈 왜곡, 카메라 기울기, 축척 때문에 px 를 그대로 쓰면 로봇이 엉뚱한 곳을 집는다.
- 나사는 길쭉해서 **방향**까지 맞춰야 흡착 패드로 안정적으로 집을 수 있다. 너트는 방향이 의미가 없다.
- 부품 위치를 사람이 매번 지정하지 않고, **놓인 그대로 보고 집는** 흐름이 필요하다.
- 로봇 컨트롤러는 현장에서 ROS 가 아니라 **TCP·전용 프로토콜**로 붙는 경우가 많다. 그래서 비전 결과를 표준 패킷으로 보내고, 받았다는 확인(ACK)까지 받아야 한다.

**목표:** 카메라 앞에 놓인 나사·너트의 중심(mm)과 장축 방향(도)을 구해 로봇에 보내고, 시뮬레이터 속 로봇이 그 값대로 집어 분류하게 한다.

## 3. 시나리오 명세

### 3.1 등장 요소

| 요소 | 실제 / 시뮬 | 역할 |
|---|---|---|
| 작업자 | 실제 | 작업 시트 위에 나사·너트를 놓고, GUI 에서 집기 사이클을 시작 |
| 휴대폰 카메라 | 실제 | 거치대에 고정, 위에서 작업 시트를 촬영. Wi-Fi RTSP 로 영상 전송 (1280×720) |
| 작업 시트 | 실제 | A4, 네 귀퉁이 ArUco 마커. 작업 좌표계의 원점·축을 정함 |
| `vision_node` | PC | 검출 → px→mm·각도 → `/vision/detections` 발행 (10 Hz) |
| `robot_bridge` / `robot_server` | PC | TCP 송신·ACK. `robot_server` 는 실제 로봇 컨트롤러 자리 |
| Gazebo 작업 셀 | 시뮬 | UR5e + 흡착 패드, 작업 매트(A4, 실제 시트와 같은 원점), 나사 상자·너트 상자 |

### 3.2 사전 조건

1. 카메라 내부 파라미터(`intrinsics.npz`)와 작업 시트 호모그래피(`homography.npz`)가 있고, 패킷의 `calib_ok` 가 true.
2. 거치대와 시트가 보정 이후 움직이지 않았다. 움직였으면 시트 1장을 다시 찍고 호모그래피만 다시 계산한다 (명령 1번).
3. Gazebo·MoveIt 이 떠 있고, `robot_server --publish-ros` 가 실행 중.

### 3.3 정상 흐름

| 단계 | 동작 | 관련 노드·파일 |
|---|---|---|
| 1 | 작업자가 시트 위에 나사·너트를 서로 떨어뜨려 놓는다 | — |
| 2 | 카메라 영상에서 시트 안쪽(ROI)만 보고 금속 부품을 분리, 회전 박스(`minAreaRect`)로 중심·장축을 구한다 | `camera_stream`, `vision_detector` |
| 3 | 중심과 장축 양 끝점을 mm 로 바꾸고, 각도를 [0°, 180°) 로 계산한다. 길이 비로 나사/너트를 판정한다 | `calibrator` |
| 4 | 패킷(JSON 1줄)을 `/vision/detections` 로 발행 → `robot_bridge` 가 TCP 로 송신 → ACK 수신 | `vision_node`, `packet`, `robot_bridge` |
| 5 | GUI 에 영상·좌표·각도·종류·송수신 기록이 실시간으로 표시된다 | `gui/main_window` |
| 6 | 작업자가 사이클 시작(`/sim/run_cycle`) → 그 순간의 최신 패킷 1장 사용 | `pick_place_node` |
| 7 | 인식한 위치·각도대로 Gazebo 에 부품 생성 (최대 3개) | `object_spawner` |
| 8 | 부품마다: 10 cm 위 접근 → 2 mm 위까지 하강 → 흡착 → 상승 → 종류별 상자 위 → 놓기 | MoveIt2, DetachableJoint |
| 9 | 결과를 `/sim/pick_log` 와 CSV 로 기록, GUI 에 표시 | `pick_place_node` |

| 상황 | 시스템 동작 | 상태 |

## 4. 기술 선정 근거

| 결정 | 고른 것 | 대안 | 이유 | 원본 |
|---|---|---|---|---|
| 카메라 | **휴대폰 IP 카메라 (RTSP)** | USB 웹캠, 사진 파일 | 추가 비용 없음, 셋 다 바로 사용. 실시간 시연 가능. WSL 의 USB 연결(usbipd) 불필요. RTSP 31.8 fps (HTTP 7.5 fps) | [DECISIONS 7절](DECISIONS.md) |
| 렌즈 보정 | **ChArUco 보드** (모니터 전체화면) | 체커보드 인쇄 | 보드 일부가 가려져도 보이는 코너로 계산 → 화면 가장자리까지 쓰기 쉬움. 모니터는 휘지 않음 | [DECISIONS 9·10절](DECISIONS.md) |
| 왜곡 모델 | **왜곡 0 고정** | OpenCV 기본 5계수 | 같은 사진으로 비교한 결과 시트 오차 5계수 11.96 mm → 0 고정 0.71 mm. 폰이 이미 왜곡을 펴서 보냄 (8.1) | [DECISIONS 10절](DECISIONS.md) |
| px → mm | **ArUco 마커 4개 (꼭짓점 16개)** 로 호모그래피 | 모눈종이 손 클릭 | 서브픽셀 자동 검출, 손 오차 없음. 카메라가 움직여도 명령 1번으로 재계산 | [DECISIONS 9절](DECISIONS.md) |
| 각도 계산 | **mm 좌표에서** 장축 양 끝점으로 `atan2` | `minAreaRect` 각도 그대로 | OpenCV 버전마다 각도 범위 규칙이 다르고, 비스듬한 카메라에선 px 각도가 찌그러짐 | [PROJECT 3.2](PROJECT.md) |
| 로봇 통신 | **TCP + JSON 1줄(NDJSON) + ACK** | ROS 토픽만 | 실제 로봇 컨트롤러는 TCP·전용 프로토콜이 많음. 시뮬레이터를 붙여도 TCP 경로·KPI 가 남음 | [PROJECT 4장](PROJECT.md) |
| 집기 방식 | **흡착 = 고정 관절 붙였다 떼기** (DetachableJoint) | 마찰 그리퍼 | 작은 나사는 Gazebo 마찰 그리퍼에서 미끄러지기 쉬워 4주 안 안정화가 어려움. 공구로 넓혀도 같은 방식 | [PROJECT 4장](PROJECT.md) |
| 시뮬 구조 | **실물 → 시뮬 디지털 트윈** (인식 위치에 가상 부품 생성) | Gazebo 가상 카메라 | 실제 카메라·보정 작업을 그대로 살림. 가상 카메라는 확장으로 검토 (10장) | [PROJECT 3.4](PROJECT.md) |
| 검출·분류 | 기준선 **규칙** + **4가지 비교 후 선택** | 처음부터 딥러닝 | 현업에서도 조명·배경이 고정된 라인은 규칙 기반이 많음. 같은 기준으로 비교한 근거로 고름 | [DECISIONS 11절](DECISIONS.md) |
| 학습 환경 | **CPU + 별도 `.venv-ml`** | GPU, Colab | GPU 없음. 가장 작은 모델로 CPU 학습 가능 확인. pip OpenCV·NumPy 가 ROS 환경을 깨지 않게 분리 | [SETUP Step 8](SETUP.md) |

**모델 비교 후보를 고른 원칙:** 단계마다 하나씩만 바꾼다 (A 규칙 → B 분류만 학습 → C 특징까지 학습 → D 검출까지 학습). 그래야 성능 차이가 무엇 때문인지 알 수 있다.
B 는 원리가 다른 k-NN·SVM·랜덤포레스트, C 는 데이터가 적어(부품 약 3천 개) 사전학습 ResNet18, D 는 각도가 필요해 회전 박스 검출인 YOLOv8n-OBB (CPU 로 학습 가능한 가장 작은 크기). [DECISIONS 11절 "후보를 이렇게 고른 이유"](DECISIONS.md)

## 5. 시스템 설계

```text
 휴대폰 카메라 (RTSP)
        │
 ┌──────▼─────────────── vision_node (ROS2) ───────────────┐
 │ camera_stream → vision_detector → calibrator(px→mm, 각도) │
 └──────┬───────────────────────────────┬──────────────────┘
        │ /vision/detections (JSON)      │ /vision/debug_image
 ┌──────▼──────┐                 ┌───────▼─────────────────┐
 │ robot_bridge │                 │ GUI (PySide6 + QThread) │◄── /robot/log, /sim/pick_log
 └──────┬──────┘                 └─────────────────────────┘
        │ TCP, NDJSON ── ACK ──┐
 ┌──────▼──────┐               │
 │ robot_server │ (가상 로봇 컨트롤러) ← 여기까지 과제 필수
 └──────┬──────┘
        │ /robot/targets
 ┌──────▼─────────┐  MoveIt2  ┌────────────────────────────┐
 │ pick_place_node │ ────────► │ Gazebo: UR5e + 흡착 패드    │
 │ /sim/run_cycle  │ ── 스폰·흡착 ►│ 작업 매트, 나사·너트 상자 │
 └────────────────┘           └────────────────────────────┘
```

- **좌표계:** 작업 시트 왼쪽 아래 = 원점, +X 오른쪽, +Y 위쪽, mm. 각도는 +X 에서 장축까지 반시계 [0°, 180°). 오차는 `min(|Δ|, 180 − |Δ|)`.
- **패킷:** `{"seq", "t_capture", "calib_ok", "objects": [{"part_type", "x_mm", "y_mm", "angle_deg", "u_px", "v_px"}]}` → 응답 `{"ack": seq, "status": "ok"}`.
- **작업 평면 → 로봇:** 설정 파일 한 곳(`sim.yaml` 의 `work_plane_x, y, z, yaw`)에서 정하고, 같은 값으로 TF 도 발행해 RViz 에서 확인.
- **분류 확장 구조:** 패킷 형식은 그대로 두고 분류기·부품 모델·상자만 늘린다 (설정에 종류 한 칸 추가 → 코드 수정 없음).

## 6. Gazebo 환경

| 구성 | 내용 | 파일 |
|---|---|---|
| 로봇 | UR5e (`ur_simulation_gz`) + MoveIt2 `move_group`, `ros2_control` | `ur5e_pick_place/launch/sim.launch.py` |

| 작업 매트 위치 | `base_link` 기준 (0.30, −0.15) m. UR5e 도달 반경(약 0.85 m) 안에서 A4 전체를 위에서 내려다보며 닿는 거리 | `config/sim.yaml` |

### 8.3 검출·분류 모델 비교 (MVTec Screws test, 2026-11-19)

공개 데이터 MVTec Screws (384장, 13종, 회전 박스 정답). train / val / test 분할을 그대로 쓰고 설정은 val 로만 골랐다. test 는 한 번만 썼다. 정답 661개, 회전 IoU ≥ 0.5.

| 방식 | 검출 F1 | 나사/너트 | **종합 F1** | 중심 오차 | 각도 오차 | CPU 시간/장 |
|---|---|---|---|---|---|---|
| A 규칙 (흑백 이진화) | 0.511 | 89.0% | 0.455 | 14.6 px | 5.46° | 6 ms |
| A 규칙 (금속 HSV, 현재) | 0.804 | 92.9% | 0.747 | 9.5 px | 5.20° | 23 ms |
| A + B-SVM | 0.804 | 100% | 0.804 | 9.5 px | 5.20° | 39 ms |
| A + C-CNN (ResNet18) | 0.804 | 98.9% | 0.795 | 9.5 px | 5.20° | 117 ms |
| **D YOLOv8n-OBB** | **0.989** | **100%** | **0.989** | **4.4 px** | **1.12°** | 98 ms |

- **병목은 분류가 아니라 검출.** 정답 박스로 분류만 하면 B·C 모두 13종 99% 이상이다.
- **YOLO 는 붙은 부품을 나눈다.** 규칙이 놓친 정답 중 "다른 부품과 합쳐짐" 62 → 2, 배경 오검출 87 → 0.
- **CNN 은 B 보다 나은 점이 없다.** 정확도는 같은데 학습 12분, 추론 약 3배.
- 학습 시간 (CPU i5-12400): B 수 초, C 약 12분, D 약 2.1시간. GPU 없이 가능.
- 노트북 (학습 과정·그래프·해석): [notebooks/model_comparison.ipynb](../notebooks/model_comparison.ipynb)

## 9. 개선 과정

| 문제 | 원인 분석 | 개선 | 결과 |

## 10. 한계 및 확장

### 한계

- **모델 비교는 공개 데이터(MVTec)에서만 했다.** 학습·시험이 같은 카메라·나무 배경이라 YOLO 에 유리하다. 우리 환경(흰 시트, 휴대폰)에서는 자체 사진으로 다시 재고 재학습해야 한다.
- **Pick 성공률은 비전 오차를 반영하지 않는다.** 인식한 위치에 가상 부품을 만들기 때문이다. 비전 정확도는 위치·각도 오차로 따로 잰다.
- 흡착은 고정 관절이라 실제 진공의 실패(기울어짐, 미끄러짐)는 재현하지 않는다.
- 카메라·시트가 움직이면 다시 보정해야 한다. 조명이 크게 바뀌면 HSV 임계값 조정이 필요할 수 있다.
- CPU 만 써서 YOLO 추론이 98 ms/장으로 10 Hz 한계에 가깝다. 집기 1회마다 검출하는 구조라 지금은 충분하다.
